# Model 2 data provenance audit

26 November 2026 · Fermentation Analytics MVP

The current Batch Monitor reads three deterministic replay fixtures from `example_data.py`. F-0607’s **119.2 g/L** forecast is the first value in its fixture tuple. The page displays that value from hour 30 through hour 36, and compares it with a fixed **130 g/L** target to show a **10.8 g/L** shortfall. The available evidence establishes how the value reaches the screen. Its origin before it was entered into the fixture remains undocumented.

## Reuse and requirements for Model 2

Reuse the three Streamlit cases as UI acceptance fixtures for forecast gating, shortfall alerts, lab reveal, and reset. Their 111 time rows represent three synthetic endpoint labels. Each trajectory is generated from its known terminal estimate, so early glucose and ethanol encode that endpoint by construction. Temperature and pH add no differences between scenarios. Splitting hourly rows would also put observations from the same batch across folds. Scores from these fixtures would not establish forecast accuracy on independent batches. The one browser replay can supply UI examples for successive issue times.

To assess the legacy generator, recover the archive and record its checksum. Read the entry point and call chain for `simulate()`, `estimate_batch()`, and `run()` and inspect any bundled exports or model files. Record dependencies, parameters, random seed handling, per-batch variation, label construction, and how the fit or predictions are produced. Run the same configuration twice in isolation and compare row counts, batch identifiers, labels, and stable output hashes or documented numeric tolerances. Compare any exported rows or forecasts with the current tuples, including the units and issue and discharge hours. The current fixture generator itself was rerun successfully. That check supplies no evidence about the older generator.

For the current MVP, add or regenerate a versioned dataset of independently varied batches, with enough batches and below-target examples in each split to evaluate errors and alerts. Record batch ID, scenario or source, observation time and availability time, process signals and units, scheduled and actual discharge time, and the discharge ethanol reference. Give each lab record separate sample and result-availability timestamps. Add forecast issue time, scheduled target time, model or baseline version, and target threshold to the prediction output. Keep any simulated terminal truth out of the feature path and use only what was available by the issue hour. Define label timing explicitly if actual and scheduled discharge differ.

Freeze the batch IDs for training, validation, and held-out testing before creating per-issue rows. Compare a recent-trend baseline with a regression using pre-issue concentrations, trends, and process readings when available. Report error by lead time, missed shortfalls, false warnings, and the number of independent batches represented in each result. Preserve generator configuration and a data manifest, plus the split, feature definitions, fitted preprocessor and estimator or reproducible fit configuration, and scored prediction export. Keep any synthetic evaluation identified as such until plant data can support a separate evaluation.
